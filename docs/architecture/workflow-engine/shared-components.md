# Shared Components — Registry and Link Model

**On this page:** The registry: `SharedComponents` · The definition chain: `SharedComponentVersions` · The link record: four fields on `Block` and `Section` · The hash/payload split · Content normalization and the comparison contract · The API surface · The reconcile loop and atomic fan-out · Composable sections and per-entry overrides · Definition writes, restore, retire · Transferring a workflow type between deployments · Agent access model · Hand-off notes for the next phases

Shared components let one block or section definition live in a deployment-wide Library and be materialized into many workflow templates as **linked copies** that can later be updated in one place. This page documents the data model that everything else builds on: the registry, the append-only definition version chain, the per-instance link record, and the canonicalization rules that keep linking invisible to content hashing while keeping it durable everywhere else.

The feature ships in phases. What exists today: the model described here, the API-boundary guards, the registry read API with the curated category vocabulary, **promote** and **materialize**, the **reconcile loop with atomic fan-out** (update-shared, adopt-head, break-out, keep-local, relink — section-scoped or [entry-scoped](#composable-sections-and-per-entry-overrides)), **composable sections with per-entry overrides** (ref entries that track Block components, hide and break-out of single entries, convert-to-ref promotion), **direct definition editing** over the API with the same fan-out, token-only **version restore**, **retire** with automatic break-out of every linked copy and inlining of every referencing definition entry, and state-only **unretire**, the flat **consumers read**, the Library page (gallery, detail, version history with diffs, restore, categories, referenced-blocks cards, a where-used table with via-section channels), and the editor's ambient link badges, gap inserts, reconcile drawer with per-entry rows, and entry-aware canvas gestures. Cross-deployment **transfer** (export / import-preview / import-apply, now with full GUI gestures — an Export-bundle action in the editor, an import dialog behind both of the editor's upload mouths, and the `/editors` list page's Import-workflow-bundle button, which creates the workflow type on a deployment that does not have it) and the **Library-side definition editor** (edit a head in place, author a new component from scratch) shipped too, as did the Library page's **promote-suggestions panel** — an on-demand scan for content repeated verbatim across templates but not yet in the Library. The suggestions scan is now served over HTTP too (`GET /shared-components/suggestions`), alongside a read-only rehearsal of a template save (`POST /workflow-templates/{typeId}/content/validate`). Still to come: a near-match suggestion tier (exact hash only today).

## The registry: `SharedComponents`

A `SharedComponent` row is pure identity and lifecycle metadata: a GUID id, a `Kind` (`Block` or `Section`, immutable), a display `Name` and optional `Description`, an optional `CategoryId`, and a `State` (`Active` or `Retired`). **The row carries no content** — the definition is exclusively the head payload of the version chain. This deliberately avoids the headless-entity pattern where content lives in a relational shadow copy that can drift from its history.

There is one global pool per deployment instance, with **no organization scoping** — components are authored by the deployment's workflow editors for the whole deployment, and write surfaces are role-gated rather than tenant-filtered. Components are retired by flipping `State`, never soft-deleted: a soft-deleted row would vanish from head lookups (the global soft-delete query filter applies) while consumer copies still point at it.

## The definition chain: `SharedComponentVersions`

Definition content lives in an append-only version chain, one linear chain per component, structurally modeled on `WorkflowVersion`:

| Column | Meaning |
|--------|---------|
| `SharedComponentId` | Plain string pointer to the registry row — no foreign key, no navigation |
| `SequenceNumber` | Position in the chain; unique per component; **the head is the highest sequence number** |
| `ContentHash` | SHA-256 (lowercase hex) of the canonical normalized definition JSON — deliberately non-unique |
| `ParentVersionId` | Self-referencing lineage edge (`NO ACTION` delete behavior — versions are never deleted) |
| `ContentJsonCompressed` | Gzipped canonical definition JSON, nullable |
| `PayloadAbsentAt` | Set on hash-only rows created by a shallow transfer import — readers must check this, never payload length |
| `CreatedByUserId` | Author stamp |

Two deliberate divergences from the `WorkflowVersion` pattern:

- **Head selection is by `SequenceNumber`, not by timestamp ordering.** Workflow versions land one row per save, so a `CreatedAt`-based ordering works there. Component chains will receive *batches* of rows in a single transaction when a transfer import fast-forwards a chain, and `CreatedAt` is client-generated, so ties are real. The unique `(SharedComponentId, SequenceNumber)` index makes head selection deterministic, enforces chain linearity structurally, and turns concurrent appends into a clean constraint violation instead of a silent fork.
- **`PayloadAbsentAt` exists from day one.** Transfer bundles carry the current content plus a hash-only ancestry trail, so imported intermediate rows legitimately have no payload. Decompressing a null payload yields an empty string, which is indistinguishable from empty content — the marker column is the only reliable signal, mirroring the reader discipline `WorkflowVersion.PayloadTrimmedAt` established.

Invariants: version rows are never deleted (soft or hard) and never retention-trimmed — **the head payload IS the definition**, there is no relational copy to fall back on, and the head row is never payload-absent. Chains stay linear: appends dedupe against the head, and diverged import lineages become conflict reports without writing rows. `ContentHash` may repeat across rows (content-identical components, or a revert re-producing an earlier hash), which is why lineage is expressed by `ParentVersionId`/`SequenceNumber` and never inferred from hashes alone.

## The link record: four fields on `Block` and `Section`

A consumer workflow embeds a **full materialized copy** of the component's content — execution, export, and hashing all see a plain workflow — plus a link record carried directly on the copied `Block` or `Section`:

| Field | Meaning |
|-------|---------|
| `SharedComponentId` | Which Library component this copy came from; `null` = plain local node (the normal case) |
| `SharedComponentLinkState` | `Linked` (live copy, kept at the component head) or `BrokenOut` (deliberately forked) |
| `SharedComponentVersionHash` | The component version materialized onto this copy; after break-out it freezes as the version-at-fork provenance |
| `SharedComponentBindings` | Definition slot tag → instance tag map written at materialization |

The lifecycle contract is the **opposite of the stable-id checklist**: these fields are copied *verbatim* by every clone, duplicate, and copy path, and are never re-minted, suffixed, or backfilled. A duplicate of a live copy is therefore another live copy of the same component, and template-to-execution clones preserve exactly what was linked at execution time. The one construction site that bypasses the reflection-based scalar copy — the parameterized-section expander — copies the four fields explicitly, plus a section's `SharedComponentSlotStates`, with the bindings and slot-state dictionaries cloned per variant so variants never alias one map. See [Object Cloning Patterns](object-cloning-patterns.md) for the underlying convention.

The same component may legitimately appear multiple times in one workflow (multiplicity is a feature, exactly like duplicate `ReplacementTag`s), so nothing may ever key a dictionary by `SharedComponentId`. A broken-out copy *keeps* its `SharedComponentId` — that is its provenance for diff-vs-origin and for the future variant matrix — and `SharedComponentLinkState` is what distinguishes live from forked; consumer queries filter on it.

The fields serialize into workflow JSON with absence-as-default semantics: an unlinked node carries none of them, `SharedComponentLinkState` travels as a string (`"Linked"`/`"BrokenOut"`) read through a tolerant converter (an unrecognized future value becomes `null` rather than poisoning the whole document), and empty bindings are omitted. They are also excluded from placeholder replacement scans — ids and hashes can contain hex substrings that collide with replacement tags by accident.

## The hash/payload split

Canonical workflow JSON serves two roles that the link fields force apart:

- **The HASH profile** feeds `ContentHash`. It suppresses the four link fields (along with entity ids, audit fields, stable ids, execution state, and transport metadata). Linking, re-linking, or breaking out a node **never changes a template's content hash** — regression baselines stay quiet, and content-hash dedup still sees plain workflows.
- **The PAYLOAD profile** is what gets stored as the version payload and served as the template representation. It **keeps** the link fields — otherwise every version-restore, save-conflict recovery, and API GET→PUT round-trip would silently strip every link in the template.

Consequently, save dedup compares **payload bytes**, not hashes: a link-only edit appends a new workflow version whose `ContentHash` is unchanged. History and restore stay faithful; baseline staleness (hash-derived) is untouched; `wasDeduped: true` remains the true-no-op signal. Stable ids now ride the same rule as the link fields: the canonicalizer treats both as *instance identity members* (`IsInstanceIdentityMember` in `CanonicalContractResolver`), excluded from the HASH profile but kept in the PAYLOAD profile — so restoring an old version or round-tripping the API preserves stable ids and link records alike, and the save backfill re-mints only genuinely absent or duplicated ids.

Component definition payloads always use the HASH profile: a definition never embeds instance link state. When section definitions become composable (per-entry references to Library blocks), those references will live on a dedicated entry type — the canonicalizer's suppressions are declaring-type-scoped to `Block` and `Section` precisely so a reference field on another type survives canonicalization. Definition-side component references must never be modeled as `Block`/`Section` link fields.

## Content normalization and the comparison contract

A component's definition content is the canonical JSON of the block or section with the **root per-consumer fields zeroed**: a block's `Order`, `ReplacementTag` and `DataOutputName`; a section's `Order`. The graft keeps each consumer's own `DataOutputName`, so two copies of one component never send data under one name. Every block's `IsCritical`, the editor's **If this block fails** setting, is per-consumer too, on a section's inner blocks as well: it is cleared from the definition and the content hash, the graft keeps each copy's own value, and a component update never changes it in another workflow. One component can stop the run in one workflow and let it continue in another, and marking a linked copy does not make it drift. The Component Library editor does not offer the setting. Two instances differing only in placement or tagging therefore produce the same definition hash, which is also what powers exact-match suggestions when bootstrapping the Library from existing templates.

**Document-class wiring is shared content, not a per-consumer field.** A section's inner blocks always carried theirs; a Block component carries its own for the same reason — the graft copies the definition's classes onto every consumer, so a definition that dropped them would silently re-wire each copy it lands in. That is also what makes converting a wired definition slot into a ref legal: the wiring travels with the component instead of being lost. Two blocks wired to different document classes are genuinely different content and hash differently.

**Presentation is not identity.** A section's `Name`, `Title`, and `GroupColor`, and a block's `Name` and `OutputTitleTemplate`, are labels rather than behavior, so they are excluded from the hash — two otherwise-identical nodes that someone titled differently, or tinted a different group colour, are the same component. Because `GroupColor` is nullable and omitted when unset, leaving it untouched would otherwise have hashed differently from explicitly choosing the default, splitting two visually identical sections. The exclusion is a third category alongside the per-consumer fields and the instance-identity members, and it is implemented differently: `SharedComponentContentNormalizer.WithoutPresentation` removes those members from the canonical JSON immediately before hashing, rather than through a `CanonicalContractResolver` profile. That is deliberate — `ToComponentCanonicalJson` produces both the stored payload and the hash input from one call, so a resolver-level suppression would strip the labels from the payload too and a freshly inserted component would land unlabelled. Every hash producer routes through `ComputeContentHashOfDefinitionJson`, so a definition hashed from a live entity and one hashed from stored JSON agree; a caller reaching past it to `WorkflowCanonicalizer.ComputeContentHash` would silently disagree with the rest of the system.

**A stored hash is identity, not content.** A stored version keeps its payload and `ContentHash` as written, and a link stamp keeps the hash it was stamped with, while a live copy is always written by today's model. When the model drops a field, every version stored before the drop keeps that field in its payload and its hash, and an untouched copy no longer hashes equal to it: `ShouldExcludeBlockOutputFromCitationSources`, dropped from the block model, made untouched copies read as local changes this way. So a live copy never compares against a stored hash. It compares against the stored payload rebuilt through today's model (`RebuildDefinitionJson`, hashed by `ComputeStoredContentHash` or `ComputeStoredSignatureInsensitiveContentHash`), found by the stored hash through `StoredVersionHashes`. The reconcile read, the local-edits gate, the whole-section push check for linked inner blocks, the relink content check, the restamp sweep, attach on promote, the attach targets of the suggestions scan, the `?contentHash=` lookup and the import preview's in-sync test all compare this way. Stamps and heads keep their stored hashes: only the comparison uses the rebuilt one.

The graft side matches: `ApplySharedDefinition` preserves the consumer's own presentation the same way it preserves `SupportedDocumentClasses` and stable ids, so a fan-out never renames a consumer's section or block. A prompt engineer can therefore retitle a linked copy to suit its host template without the copy reading as `Diverged` and without the next component update reverting the rename. The definition payload still carries the author's labels, which is what a fresh materialize lands.

**Comparing a materialized instance against its definition is only meaningful after reverse-applying the instance's bindings.** Materialization rewrites tags (definition slot tags become instance tags, both on inner blocks and inside prompt text), so raw hash comparison of a materialized instance is expected to differ. The bindings map is the translation table: reverse-bind, then normalize, then hash. This is also the fan-out correlation rule for the reconciliation phase — definition slots correlate to consumer blocks through the bindings, which is what lets fan-out rewrite consumer copies **in place** while preserving their stable ids (and with them signature overrides and regression baselines).

## The API surface

The registry is served by `SharedComponentsController` at `api/v{version}/shared-components`; operations that mutate a template are template-scoped on the workflow-templates surface. Every endpoint — reads included — requires the `WorkflowEditor` or `SuperAdmin` role, so agent service users (which carry `WorkflowEditor`) can drive the full loop. The route inventory lives in the [API reference](../../reference/api/index.md); the agent-facing contract (request/response shapes, the two concurrency tokens, error recovery) is §6 of the agent guide served at `GET /api/v1/workflow-templates/agent-guide`.

| Method | Route | Purpose |
|--------|-------|---------|
| GET | `/shared-components` | List with head tokens, category, and consumers; filters: `?contentHash=` (the attach-candidate lookup), `?categoryId=`, `?workflowTypeId=`, `?workflowTypeCategoryId=` — a blank parameter is a no-op |
| POST | `/shared-components` | Create a new component with its first version from a Library-authored definition; re-normalized and ref-validated server-side, no template anchor, no fan-out (a fresh component has no consumers) |
| GET | `/shared-components/suggestions` | Sweep every template for content repeating verbatim outside the Library, and for content already matching an active head; pure read |
| GET | `/shared-components/{id}` | One component's summary |
| GET | `/shared-components/{id}/consumers` | The workflow types holding live linked copies — direct copies and copies reached through ref entries of linked sections, each row annotated with its `channel` and the section it arrives through |
| GET | `/shared-components/{id}/consumer-matrix` | Section components only: the consumers×entries grid — one row per live linked copy, one column per definition entry plus any locally inserted slot; a block component is refused with `SharedComponent.KindMismatch` rather than returning an empty grid |
| GET | `/shared-components/{id}/content` | The head definition JSON verbatim, plus `headVersionId`/`headContentHash` |
| GET | `/shared-components/{id}/versions` | History, newest first; `payloadAbsent` flags hash-only lineage rows; `?includeNarratives=true` adds per-version change summaries |
| GET | `/shared-components/{id}/versions/{versionId}/content` | One stored version's definition JSON |
| PUT | `/shared-components/{id}/content` | Replace the definition: new head plus atomic fan-out to every linked copy |
| POST | `/shared-components/{id}/reconcile-preview` | Advisory impact preview; optional draft definition in the body |
| POST | `/shared-components/{id}/versions/{versionId}/restore` | Token-only restore of a stored version as the new head, fan-out included |
| POST | `/shared-components/{id}/retire` | Freeze the component; break out every linked copy and inline its ref entries in section definitions, atomically |
| POST | `/shared-components/{id}/unretire` | Reactivate; state-only |
| GET/PUT/DELETE | `/shared-components/categories(/{categoryId})` | The curated category vocabulary; delete refuses while components reference the entry |
| PUT | `/shared-components/{id}/category` | Re-file a component under a category |
| POST | `/workflow-templates/{typeId}/shared-components/promote` | Publish a template node as a new component (or attach to an existing one) and stamp the node's link record |
| POST | `/workflow-templates/{typeId}/shared-components/materialize` | Copy a component's head definition into the template as a new linked node |
| GET | `/workflow-templates/{typeId}/shared-components/reconcile` | Classify every linked/broken-out node against the registry; pure read |
| POST | `/workflow-templates/{typeId}/shared-components/reconcile/apply` | Apply a batch of per-node decisions atomically, with every fan-out they trigger |

History responses expose `ContentHash`/`ParentVersionId` lineage and keep `SequenceNumber` deployment-internal — hashes are the only identity that survives crossing deployments. `consumerCount` counts `Linked` copies in Core templates only (broken-out copies are excluded), which stays accurate because a template save hard-deletes and reinserts its node rows. For a Block component the count includes copies reached indirectly as ref entries of linked section copies; `viaSectionConsumerCount` on the summary reports that subset. Categories are a flat curated vocabulary (`SharedComponentCategory`, stable kebab-case ids); components reference it by id, dangling references are structurally impossible (re-categorize validates, delete refuses while referenced), and components predating the catalogue simply carry `null`.

**Overwriting a consumer's local edits is gated.** A fan-out replaces content in every linked copy, and a copy whose content matches neither the incoming head nor its own recorded link stamp — the `LocalAhead`/`Diverged` shapes the reconcile surface offers `KeepLocal` for — holds work no decision named. The gate evaluates every linked shape before grafting: an edited instance of a Block component, an edited inline entry inside a linked section copy (`SharedComponentReconciler.OverwrittenInlineSlots`, compared per entry against the stamped old definition and the incoming one), and an edited `ComponentRef` entry that grafting re-materializes from the referenced block component's head (`SectionReconcileResult.OverwrittenLocalRefSlots`). The fan-out refuses with a 409 `SharedComponent.OverwritesLocalEntries` naming the workflow type and slots, released per component by `acknowledgeOverwrittenEntries`. Signature-field differences alone never trip the gate: stored consumer copies hold signature fields hoisted to workflow level while definitions carry them per block, so the comparison hashes both sides without them (`ComputeSignatureInsensitiveContentHash`) — signature collateral has its own orphan gate. Entries an explicit decision names are exempt by construction (their content equals the head the decision lands), as are broken-out slots, hidden slots, and blocks not yet linked to that component (a first-time slot convert) — only content already tracking the component can hold divergence against it.

**Finding candidates.** `GET /shared-components/suggestions` (`ScanSharedComponentBootstrapQuery`) sweeps every workflow type's graph and groups nodes by normalized content hash, reporting a group when the content occurs in two or more places or already matches an active component's head. Reserved deployment pseudo-types are skipped exactly as the template list skips them, so every node names a template a caller can read and save. It is the bootstrap path for a deployment whose templates were hand-copied before the Library existed, and it is also the only practical way for an API caller to answer "does this already exist as a component?" — the `?contentHash=` attach-candidate filter needs the server-side **normalized** hash, which is not the hash of any JSON the caller holds. Matching is exact, never fuzzy, so a group is always safe to collapse. Candidates exclude actively Linked nodes, and blocks inside an actively Linked section belong to that section's component rather than standing alone; a broken-out copy is a candidate again and discloses its origin in `provenanceComponentId`. `existingComponentId` on a group decides the shape of the follow-up: set means attach every node to it, absent means promote one node and attach the rest to the id promote returns — the same split the Library page's Scan button makes (`BootstrapSuggestionPlanner.SplitDispatch`). Both mouths run the one query, which loads every template graph and reports `scannedWorkflowTypeCount`/`elapsedMilliseconds` so the cost of that sweep is visible rather than implied.

**Addressing.** Promote and every reconcile decision name a node by exactly one of two locators. `targetPath` is the canonical node path `Sections[i].Blocks[j]`, with indices meaning order-sorted rank (resolution never renumbers a gapped legacy template, since normalizing `Order` would change content bytes). `targetStableId` addresses by the node's stable id, which since the payload-profile change is served in the template JSON and survives reorders. The error channel keeps the two failure kinds apart: a malformed or ambiguous locator (both forms, neither, unparseable path) is a 400 `SharedComponent.InvalidTargetLocator` — fix the request; a well-formed locator that addresses nothing is a 404 `SharedComponent.TargetNotFound` with the template's section/block counts as self-correction metadata — the template moved, re-read it.

**Promote** loads the live template graph (not canonical JSON — a canonical load would null every stable id and the save backfill would re-mint them all, orphaning signature overrides), validates the node (no link record, or a broken-out copy outside an actively linked section, whose old link fields and slot overrides the promote replaces; sections must have unique non-empty inner `ReplacementTag`s and no expanded parameterized variants; blocks must not sit inside an expanded parameterized variant), builds the normalized definition, and then performs the registry insert and the link-stamping template save **atomically**: the component and version rows ride as pending context-level adds that the template save's own transaction flushes, so a stale `baseVersionId` (409) or any save failure leaves zero registry rows. A link-only promote appends a template version with an unchanged `ContentHash` (`wasDeduped: false`). With `attachToComponentId` the node joins an existing component instead: its normalized hash must equal the head's (`409 SharedComponent.ContentMismatch` with `expectedHash`/`actualHash` otherwise), and nothing is written to the registry. Attach matches across differing placement and tags because normalization zeroes the per-consumer fields. An optional `categoryId` files the new component under an existing vocabulary entry at creation. A section promotes with its Linked inner blocks: normalization derives each into a `ComponentRef` entry, so the new component references those Block components (always tracking their heads) instead of baking their content in; broken-out inner copies are baked in verbatim.

Promoting a block that sits **inside a Linked section copy** is the convert-to-ref path: besides creating (or attaching to) the Block component, the handler resolves the block's definition slot through the container's bindings and rewrites the container component's definition, turning that slot from inline into a `ComponentRef` — a new container head that fans out to every consumer of the section in the same transaction as the registry insert (`ConvertContainerSlotToRefAsync` in the promote handler). This second write is guarded by its own token, `expectedContainerHeadVersionId`, required exactly in this case: a stale or missing value is a 409 `SharedComponent.HeadMoved` carrying `containerComponentId` and `containerHeadVersionId` in the problem details. The anchor template's `baseVersionId` is validated up front, and its own save lands as one of the fan-out's consumer saves. A slot's document-class wiring no longer blocks the convert: a Block component carries its own classes, so the wiring moves into the component and the graft reapplies it to every consumer instead of being dropped. The convert still refuses a slot whose live block has drifted from the definition (`SharedComponent.ContentMismatch` — reconcile the section first) or one carrying a recorded per-entry override (`SharedComponent.InvalidLinkShape`).

**Materialize** loads the component head (payload-absent → 409), deserializes the definition, and lands it through the same domain helpers user copies use — block copies re-mint their stable ids deterministically before the save. A block component's target must be a content section: separators and expanded parameterized variants are rejected. A Linked section copy is a legal target — the landed block is its own Linked copy that the container's definition does not track, so the entry surface classifies it as a local insert. The instance tag is the requested `replacementTag` (400 on a workflow-wide collision) or an auto-slug of the component name; colliding inner slot tags are renamed `{slot}_{n}` and the renames recorded in `SharedComponentBindings` (absent key = identity). External references in prompt text stay verbatim — the response's `warnings[]` (the standard structural-validation warnings, run post-insert) surface dangling tag references and document classes the target template lacks. Both writes carry the template's `baseVersionId` and 409 on staleness exactly like the content PUT.

## The reconcile loop and atomic fan-out

The reconcile **read** (`GET …/shared-components/reconcile`) classifies every node carrying a link record against the live registry: each row exposes both locators, the link state, the instance/link/head content-hash triple, a relation (`InSync`, `LocalAhead`, `HeadAhead`, `Diverged`, `ComponentMissing`, `ComponentRetired` — computed after reverse-applying the instance's bindings), the sanctioned decisions ordered default-first, a `linkHashStale` flag (the copy's content is already at the head but its stamp lags; a fan-out — including the apply's own restamp sweep — heals it), `hasLocalOverrides` (recorded slot overrides or private extra blocks were reconstructed out of the instance hash — the copy deviates deliberately even when the relation reads `InSync`), and `localInsertCount` (how many entry rows are local inserts). Rows for Linked section copies additionally carry [per-entry rows](#composable-sections-and-per-entry-overrides). The response's `baseVersionId` is the anchor token the apply must echo.

The reconcile **apply** takes a batch of per-node decisions — `UpdateShared`, `AdoptHead`, `BreakOut`, `KeepLocal`, `Relink`; every arm but `Relink` also comes [entry-scoped](#composable-sections-and-per-entry-overrides) — and lands everything in **one transaction**: the anchor template saves first under the caller's `baseVersionId`, each `UpdateShared` appends the instance's reverse-normalized content as the component's new head, and every `Linked` consumer of that component is grafted and saved — including instances and templates the decision batch never mentioned. Non-anchor consumers save tokenless; a racing rival edit trips the pipeline's guard and rolls the whole apply back. `UpdateShared`, `AdoptHead`, and `Relink` echo the component head they were decided against via `expectedHeadVersionId` (stale → 409 `SharedComponent.HeadMoved`); contradictory decisions (two on one node, update-plus-keep-local on one component, or multiple `UpdateShared` with differing content) are refused as `SharedComponent.ConflictingDecisions`. Fan-out consumer versions are attributed to the applying user.

The same engine (`SharedComponentFanOutService`) serves the definition PUT and version restore: **any component write is an append plus an immediate atomic fan-out**, so a linked copy is always at its component's head — the no-pinning invariant is enforced by construction, not by a background job. Grafting rewrites consumer copies **in place** through `ApplySharedDefinition` and the slot reconciler (bindings-correlated, with hash-equality rename rescue and local-extra-block re-slotting), never through the re-minting copy helpers, so stable ids — and with them signature overrides and regression baselines — survive every fan-out. Document-class wiring rides the graft: `ApplySharedDefinition` copies `SupportedDocumentClasses` from the definition, matching the normalizer's wiring-is-shared-content contract, while presentation (a block's `Name` and `OutputTitleTemplate`) stays the consumer's own. The graft also enforces the definition's declared shape on inline slots: a live block occupying a definition-inline slot has any leftover Library link of its own cleared, so a slot-convert followed by a restore cannot leave a copy carrying links its definition does not declare. A definition byte-identical to the head is a dedup no-op (`wasDeduped: true`, nothing fanned out).

Atomicity mechanics worth knowing: the new component version rides as a **context-level pending add** that the first consumer save's transaction flushes (a failure detaches it, so the context stays clean for a retry); a rival append materializes as a unique-index violation on `(SharedComponentId, SequenceNumber)`, classified by inspecting the failed entries — never by SQLSTATE — and reported as 409 `SharedComponent.ConcurrentAppend` with the current head in the problem details; and the engine **rolls the transaction back before re-reading the head**, because on PostgreSQL a query on an aborted transaction fails with `25P02`. All of this is proven against live PostgreSQL and SQL Server by the env-gated `SharedComponentFanOutAtomicityTests` (a mid-transaction failure after the first consumer save leaves the chain, both consumers, and their version histories untouched, and the same service instance retries successfully).

**Orphaned signature overrides gate every write.** A definition change that removes a slot deletes the client override rows keyed to that slot's blocks; one that drops a placeholder leaves rows inert. Any write that would do either is refused with 409 `SharedComponent.OrphansNeedAcknowledgement`, listing the affected rows in the problem details; the caller re-sends with `acknowledgeSignatureOrphans: true`. The orphan set is re-computed inside the write transaction — never trusted from a preview — so the acknowledged list is the applied list. The advisory `reconcile-preview` reports the same impact (consumers, regression baselines whose freshness a fan-out would stale, the orphan set, and the slot delta for sections) without writing anything.

## Composable sections and per-entry overrides

A section definition is a manifest of **entries** (`SectionEntry`: `SlotTag`, a `Kind` of `Inline` or `ComponentRef`, `SharedComponentId`, `Bindings`). When a section promotes, the normalizer's `DeriveEntries` turns each Linked inner block into a `ComponentRef` entry pointing at that block's own component and strips the block from the stored `Blocks` — the definition references the Block component instead of baking its content in — while inline blocks stay stored as blocks. `Entries` is emitted only when at least one ref exists; a ref-free definition stores plain blocks and synthesizes inline entries on demand through `Section.EffectiveEntries()`. Ref entries carry no version pin — they always mean the referenced component's **current head**. No extra machinery makes that true transitively: the materialized inner block of a ref entry in a consumer template is itself an ordinary Linked copy of the Block component, so editing that component fans out to it exactly like to any direct copy; the section definition stores only the reference and needs no rewrite.

On a consumer's Linked section copy, per-entry deviations ride `Section.SharedComponentSlotStates` — a slot-tag → `Hidden` | `BrokenOut` map (`SharedComponentSlotState`). `Hidden` means the definition entry is suppressed in this workflow (no live block); `BrokenOut` means the slot's live block is deliberately forked while the section as a whole stays Linked; absence means the entry follows the definition. Fan-out grafts honor the map — a hidden slot stays out, a broken-out slot keeps its fork. The structural validator admits `SharedComponentSlotStates` only on a link-carrying section and only with those two values, and rejects `Entries` anywhere in template JSON (definition-payload vocabulary — templates carry materialized blocks).

Because overrides and private additions are sanctioned deviations, comparing such a copy raw would read `Diverged` (or `LocalAhead`) forever. The reconciler therefore hashes deviating copies through `SharedComponentContentNormalizer.ReconstructDefinitionJson`, which backfills hidden and broken-out slots from the definition (ref slots as synthesized placeholder ref blocks) and strips extra blocks that belong to no definition slot before hashing — so a copy whose only deviations are its overrides or its own added blocks classifies `InSync` or `HeadAhead`, not `LocalAhead`/`Diverged`, with the additions disclosed through `localInsertCount`. Extras are recognized only when every definition slot is accounted for in the instance — by a `SharedComponentBindings` record, a slot-state record, or a block at the identity tag; a copy missing a definition slot without a tombstone, or carrying duplicate tags, stays on the raw hash and reads as drift. A raw hash already equal to the head short-circuits all of this: a copy sitting byte-identical at the head classifies `InSync` (with `linkHashStale` when only the stamp lags) before any reconstruction runs. Classification reconstructs against the definition the copy is stamped at; the `Relink` content guard reconstructs against the head being relinked to — so a broken-out copy whose shared content matches the head relinks cleanly even when it carries private extra blocks, and those blocks survive the relink untouched.

The reconcile read expands Linked section copies (and only those — a broken-out section carries no entry surface) into per-entry rows: a locator (`entryStableId` when a live block exists, `entryKey` otherwise — hidden and locally-deleted entries have no live block), the entry's origin (definition-stored inline slot, definition ref, or local insert), its override state, its own relation, `entryAvailableActions`, and — for a Library-linked local insert — `insertLinkState`, so a reader can tell a forked insert from a live one without a second query. An inline entry's relation is a per-slot three-way compare of the live block against the head's slot and the link-stamped old definition's slot; when the old definition cannot be resolved (foreign or payload-absent link hash) an edited entry reads `Diverged`, not `LocalAhead` — with no evidence of which side moved, the classification stays conservative, mirroring the whole-instance rule:

| Entry situation | Sanctioned decisions (menu order) |
|---|---|
| Hidden here | `KeepLocal`, `Unhide` |
| Broken out here | `KeepLocal`, `AdoptHead` |
| Live block deleted here (not hidden) | `Hide`, `AdoptHead`, `KeepLocal` |
| Removed from the definition head | `KeepLocal`, `UpdateShared` |
| Local insert | the node-level arms minus `Relink`, plus `UpdateShared` |
| Ref target missing or retired | `KeepLocal`, `BreakOut` |
| `LocalAhead` | `KeepLocal`, `UpdateShared`, `AdoptHead`, `BreakOut` |
| `HeadAhead` | `AdoptHead`, `BreakOut`, `KeepLocal` |
| `Diverged` | `UpdateShared`, `AdoptHead`, `BreakOut`, `KeepLocal` |
| `InSync` | `KeepLocal` |

The ordering is a menu (default-first), not a recommendation engine — the editor's preselect policy is deliberately more conservative (see [Editor State Model](editor-state-model.md)).

A decision becomes entry-scoped by adding exactly one entry locator to the same decision record — `entryKey` or `entryStableId`, both is a 400 `SharedComponent.InvalidTargetLocator`, and `Hide`/`Unhide` (the only two arms that exist solely per-entry) require one. Entry decisions are accepted only on Linked section copies, and `Relink` is never entry-scoped — adopt the head for the entry instead. The token model: an entry-scoped `UpdateShared` or `AdoptHead` carries `expectedHeadVersionId` (the **section** component's head, same as any section-scoped decision) and, when the entry is a definition ref, additionally `expectedRefHeadVersionId` (the referenced Block component's head — stale is a 409 `SharedComponent.HeadMoved` whose metadata names `expectedRefHeadVersionId` as the stale token). `Hide`, `Unhide`, `BreakOut`, and `KeepLocal` are tokenless. No entry-specific error codes exist — entry failures reuse `InvalidTargetLocator` and `HeadMoved`.

**Hide** tombstones a definition-provided slot (`SlotStates[slot] = Hidden`), removes the live block and its binding, and leaves the section Linked; broken-out slots and local inserts are refused (adopt or fork the former, plain-delete the latter). **Unhide** clears the tombstone and rematerializes the slot from the **current** head — a ref entry lands as a fresh Linked copy of the ref component's current head, and a slot that no longer exists at the head simply clears with nothing to restore. Both are idempotent. **Relink** on a broken-out section that still carries overrides first passes the deviation-cancelling content guard, then clears the whole override map: hidden slots rematerialize from the current head, broken-out inline slots are grafted back to the head definition keeping their stable ids, broken-out ref slots reconnect to the ref component's current head (tokenless — the section-level `expectedHeadVersionId` anchors the decision), slots gone from the head drop, and local-insert blocks survive untouched. The HTTP apply response reports only the decision outcome echo — the per-slot clearing is not on the wire; the editor derives the clearance list from the loaded workflow's own override map and confirms it before dispatching.

When a definition changes shape, the slot reconciler correlates old slots to new ones in tiers: exact tag match first, then an unambiguous hash-equality rename rescue, then a fuzzy rescue restricted to inline entries of the same block type — a unique case-insensitive block-name match, else same relative position with tag similarity at or above `TAG_SIMILARITY_RESCUE_THRESHOLD` (0.6, normalized Levenshtein). Whatever remains unclaimed is a removal or an addition — with one identity check before an addition materializes: a slot new to the definition first claims an unclaimed instance block already carrying that slot's tag when it is provably the same thing (content-hash equality for inline slots, component identity for refs). That is the whole-section-push anchor case — the pusher's own just-added block would otherwise land a second time under a uniqued tag; a same-tag block with genuinely different local content still dodges to a unique tag and keeps both. Rescues are reported per-rescue with their reason on the `reconcile-preview` response (`slotDelta.rescuedSlots`); at graft time they fold into the rename map, so the consumer's block survives under the new slot with its stable id — and its signature overrides — intact. A graft that cannot resolve the old definition (foreign link hash) correlates through the instance's bindings and never removes anything. A graft that cannot resolve a `ComponentRef` entry's **head** (no target id, or the target resolves to nothing materializable) also stays non-throwing — a matched copy is kept at its old content, a brand-new ref slot lands nothing — but the arms disclose themselves: the section reconcile result carries `StaleRefSlots` / `DroppedRefSlots` and the fan-out logs a warning per affected section (a deliberately broken-out slot is neither). Loud failure stays at the mouths — materialize and adopt-head refuse unresolvable refs outright.

The consumer scan behind `consumerCount` and the consumers read (`SharedComponentConsumerScan`) merges direct copies and ref-entry-reached copies per workflow type; a type with any direct copy reports as `Direct`, otherwise as `ViaSection` naming the section component it arrives through. The channel annotation is served on the wire as well as in-process: each `GET …/consumers` row carries `channel` plus `viaSharedComponentId`/`viaSharedComponentName`, so an agent sees exactly what the Library page's where-used table sees. The same scan also reports `brokenOutInstanceCount` per component — copies that keep the component id as provenance but no longer follow the head, deliberately excluded from `consumerCount`.

**The consumers×entries matrix** (`GET …/consumer-matrix`, `GetSharedComponentConsumerMatrixQuery`) answers "which copies deviate, and where" for a section component. Columns are the head definition's entries in definition order, followed by any slot a consumer filled locally (`isLocalOnly`). Rows are live linked copies — one row per **copy**, so a type holding two appears twice, distinguished by `stableSectionId`; broken-out copies are not rows. Cells read `Live`, `Custom` (that entry broke out), `Hidden`, `Added`, `Missing`, or `NotApplicable` (a local-only column another copy introduced). Cell correlation runs through each copy's `SharedComponentBindings`: a slot whose tag was auto-renamed at materialize reads by its definition column, and a bound live tag is never mistaken for a local insert.

The query is deliberately cheap, and the reason is the propagation invariant: a persisted `Linked` copy is **always** at the component's current version, so a linked entry cannot have silently drifted. Deviation is therefore representable only as a `SharedComponentSlotStates` entry (`Hidden`/`BrokenOut`) or an absent block — every cell is a field read. That is why this query loads no consumer workflow graph and hashes nothing, unlike the reconcile read, which walks the opposite direction (one workflow to its links) and must compare content. A test pins the handler's only dependency as the unit of work so the expensive path cannot creep back in.

## Definition writes, restore, retire

`PUT /shared-components/{id}/content` replaces the definition wholesale: the server re-normalizes the submitted JSON (per-consumer fields and any link fields are stripped before storing), appends the new head under the caller's `expectedHeadVersionId`, and fans out. `POST …/versions/{versionId}/restore` is **token-only by design** — the server re-appends its own stored payload, so callers never round-trip definition content; restoring the current head is a dedup no-op, and a `payloadAbsent` row cannot be restored (409). A restored head repeats the old version's content hash — legal, which is why lineage is never inferred from hashes.

**Retire** freezes the component and breaks out **all** linked copies in the same transaction — a retired component has zero linked consumers by construction, each copy keeping its content and provenance (`BrokenOut` + version-at-fork hash). Retiring a **Block** component also sweeps section **definitions**: every Section component whose head carries a `ComponentRef` entry pointing at it gets a new head appended with that slot baked back inline (the retired head's content replaces the ref entry), so no definition references a retired component either. Linked copies of those containers restamp to the baked hash without a graft — their materialized inner block already carries the content and has just broken out — and the response lists the rewritten containers in `inlinedContainerIds`. **Unretire** is state-only: broken-out copies stay broken out, inlined definitions stay inlined; new consumers arrive by materializing again or by a `Relink` decision. Both are idempotent. While retired, definition writes and new links are refused with 409 `SharedComponent.Retired`, and the reconcile read's relation turns `ComponentRetired`.

**GUI flow.** The editor's Share affordances, the gap-mounted "From Library…" inserts, the link badges, the reconcile drawer with its per-entry rows, the entry-aware canvas gestures (hide from the canvas, convert-to-ref), and the `/library` page (gallery, detail, version history with diffs, restore, retire/unretire, categories, referenced-blocks cards, the where-used table, the promote-suggestions panel) are all thin clients over the same commands. Every editor-side write dispatches against the saved head and ends in a **mandatory reload** of the just-written version, because a later save from the stale in-memory graph would silently erase the server-side changes. Share and the "From Library…" inserts save first (the versioned save dedups to a no-op when the editor is clean). The reconcile drawer does not: opening it writes nothing and compares the last saved version, and its Apply refuses while the editor's content differs from the head, so the post-apply reload cannot discard unsaved edits. The Library page also **edits and creates definitions directly**: the detail view's Edit button mounts the head on the shared editing surface (a Block component as one block, a Section component with its inline blocks and `ComponentRef` slots composing in place — refs render as cards with swap/remove, and "From Library…" drops a linked placeholder), Save previews the blast radius in an impact-review dialog and submits the same `SaveSharedComponentContentCommand` the API PUT drives; a New-component flow authors from scratch and lands the first version through `CreateSharedComponentCommand`. The editor-side state model (the link index, badge semantics, drawer, the Library editor's capability hosts) is documented in [Editor State Model](editor-state-model.md).

**Retire-not-delete is enforced structurally.** `CoreDbContext` overrides its `SaveChanges`/`SaveChangesAsync` entry points and rejects any tracked hard-delete or soft-delete (`IsDeleted`) of a `SharedComponent` or `SharedComponentVersion`; flipping `State` to `Retired` passes. Raw SQL and `ExecuteDelete` bypass the change tracker and remain out of guard reach — no code path issues them against these tables.

## Transferring a workflow type between deployments

A workflow type moves between deployments as a self-contained **bundle**. Three `EDITOR_ROLES`-gated endpoints on the template controller drive it: `GET …/export` produces the bundle, `POST …/import-preview` classifies it against the target read-only, and `POST …/import-apply` applies it in one transaction. The two sides are peers — relatedness is computed from content hash trails at import time, never assumed from which deployment exported. Import **creates the target when it is absent** — porting a type onto a deployment that does not have it is the mission the feature serves. An absent (or headless) target is not an error: preview returns a create-shaped result (`template.relation = New`, `baseVersionId = null`, components still correlated against the target's Library, since a component can pre-exist without the type), and apply creates the `WorkflowType` from the bundle's `workflowTypeName` / `workflowTypeDescription`, seeds the importing organization's access row, and lands the bundle's template as the first version — inside the same transaction as the component fan-out. A create apply omits `baseVersionId`; if the target grew a template head between preview and apply, the first-version save fails the base-version check and the whole apply rolls back — re-preview. A bundle predating the name field cannot create a type (`SharedComponent.BundleTypeNameMissing`) — re-export it from the origin.

The bundle (`WorkflowTransferBundle`, a contracts DTO — not a `Workflow` property) carries the template's stored canonical payload verbatim, the workflow type's display name and description (`workflowTypeName` / `workflowTypeDescription` — what a create-import names the type; the type's *category* deliberately does not travel, matching the carriers philosophy below), its version content-hash trail (oldest→head), every shared component the template depends on (each at its head definition plus its own trail), and the categories those components reference. `bundleFormatVersion` (1) guards the envelope independently of the template's own `FormatVersion`.

**The dependency closure is depth-1.** Export collects `{actively-linked components} ∪ {ref targets of linked section heads}` (`SharedComponentClosure`) and stops there — provably one hop, not a fixed-point walk: a linked *section* head may name *block* components through its `ComponentRef` entries (`SharedComponentRefHeads.CollectRefTargetIds`), but blocks are leaves (no entries) and a section referencing a section is blocked by the kind guard. Import re-validates completeness — a bundled section whose ref target the bundle does not carry is corrupt or hand-edited and is rejected whole with `SharedComponent.CorruptDefinition`.

**Correlation finds each bundle component's local counterpart** through four tiers, first hit wins (`SharedComponentCorrelator`), because ids are re-minted on every edit and are never read as identity: **Anchor** (the local template node at the same stable id links a local component of the same kind), **HashTrail** (the bundle trail overlaps the local chain's hashes, kind-equal — shared history *is* identity), **GuidEquality** (a local component already holds the bundle id with the same kind — common origin, not chance), else **Create** (new here; adopts the bundle id when free). The preview relation is computed on top: `InSync`, `LocalAhead` / `BundleAhead` (one head descends from the other by raw trail membership), `Diverged`, or `LocalRetired`. A Section-kind row can additionally carry `refWarnings[]` — one advisory string per `ComponentRef` target that would not survive the apply as-is (its local counterpart is retired, payload-absent, or not a Block component), each embedding the code the apply would fail with; preview reports, apply enforces. Each correlated row also carries `localHeadVersionId` — the token a take-theirs decision must echo back as `expectedLocalHeadVersionId` — so a legal apply can be built from the preview alone.

**The ref-id subtlety.** A section definition's canonical bytes *include* its `ComponentRef` target ids — `SectionEntry.SharedComponentId` sits outside every canonicalizer suppression set — so two structurally identical sections whose ref targets have different local ids hash differently. `InSync` is therefore a **normalized compare**: the bundle head's ref ids are substituted through the correlation map (`SharedComponentTransferCompare.LocalizeHeadDefinition`, a byte-preserving value swap) before hashing, so id differences alone never force a false `Diverged`. Raw trail ancestry still degrades in that corner — a related section reads `Diverged` conservatively, disclosed by the correlation method, and the arms resolve it. Templates are immune (instance link ids are hash-suppressed); block components are immune (leaves).

**Apply is one transaction.** On a create import that transaction additionally inserts the `WorkflowType` row and the importing organization's access row before the first-version save. New components are created; each **take-theirs** component appends the bundle head as its new local head and grafts *every* local consumer (full fan-out, like a Library push), unless the bundle head already matches — an idempotent re-import no-ops per element (`Deduped`). The template arm saves the bundle's content (link ids mapped through the correlation and restamped to the post-append local heads; the template content hash is unaffected because the quartet is hash-suppressed) or, on keep-mine, rides only the grafts' restamps. Previews go stale by design, so apply re-checks inside the transaction and 409s on a moved head (`HeadMoved`), a zero-overlap take-theirs the caller did not acknowledge (`DivergedLineage`, gated by `acknowledgeUnrelatedHistory`), a landed template that would link a retired local component (`Retired`), or newly orphaned signature overrides (`OrphansNeedAcknowledgement`); a lost race is `ConcurrentAppend`. Every Section-kind component the apply lands (created or appended) also has its `ComponentRef` targets validated against the **post-apply merged set** — the local registry plus the bundle's own creates and appends under the caller's per-component decisions — failing the whole apply loud before anything is written: `UnknownComponent`, `KindMismatch` (only a tampered bundle can produce it, export refuses non-Block targets), `Retired` (the target stays retired under a keep-mine decision), or `PayloadAbsent` (the kept local head has no stored payload). What a bundle never carries — organization access, signature field values, counterparty maps (the carrier named `Company maps`), and execution history and regression baselines — is disclosed as `skippedCarriers` on both import responses.

## Agent access model

The workflow-template HTTP API treats the link fields as **reserved, server-managed metadata** (see the agent guide served at `GET /api/v1/workflow-templates/agent-guide`):

- The template-content GET serves them verbatim inside the workflow JSON; clients must round-trip them unchanged. Editing the *content* of a linked node is allowed — the copy diverges locally (`LocalAhead` in the reconcile read), and the reconcile endpoints resolve it: push the edit to the Library, adopt the head back, or break the link.
- The content PUT endpoint rejects fabrication with path-keyed 400s, in two layers. Shape violations are caught on the raw JSON by the structural validator (link fields present without `SharedComponentId`, a `SharedComponentId` without a `SharedComponentLinkState` — the implication holds in both directions, so a half-linked node can never persist — a `SharedComponentLinkState` outside `Linked`/`BrokenOut`, a malformed 64-hex `SharedComponentVersionHash`, non-string bindings values, `Entries` in template JSON (definition-payload vocabulary — templates carry materialized blocks), `SharedComponentSlotStates` anywhere but a link-carrying section or with values outside `Hidden`/`BrokenOut`) — deliberately *before* deserialization, because the tolerant enum converter would otherwise silently null an unknown state and a malformed bindings object would abort deserialization into a generic error. Referential violations (a `SharedComponentId` with no registry row, or one whose `Kind` doesn't match the node) are checked by the save handler in one batched query.
- Error codes form the `SharedComponent.*` family, declared in `SharedComponentErrorCodes`. On the validation channel the JSON path is the error key and the family code rides in the message (`InvalidLinkShape`, `KindMismatch`, `InvalidTargetLocator`, `ConflictingDecisions`); the conflict/not-found channel carries the code in the problem-details `code` extension, alongside self-correction metadata in further extensions (`UnknownComponent`, `UnknownVersion`, `TargetNotFound`, `AlreadyShared`, `Retired`, `ContentMismatch`, `PayloadAbsent` — 404 on reads, 409 on write preconditions — `NoVersions`, `HeadMoved`, `ConcurrentAppend`, `OrphansNeedAcknowledgement`, `OverwritesLocalEntries`, `UnknownCategory`, `CategoryInUse`, `CorruptDefinition`, for cross-deployment transfer — `DivergedLineage`, `BundleFormatUnsupported`, and `BundleTypeNameMissing` — and for the agent-block guard — `AgentRuntimeDisabled`, `AgentExpansionScope`, and `AgentBlockInvalid`). The agent guide's §6 carries the per-code recovery table and §8 the transfer flow.
- The guard is **enforced only at the API boundary by design**. The Blazor editor cannot author link fields and already bypasses structural validation; editor-side ingress of foreign link fields (file upload, version restore) is what the reconcile loop handles gracefully — a link whose component id resolves to nothing classifies as `ComponentMissing` and the drawer offers break-out, never a hard failure. Moving a whole type with its links intact between deployments is what the transfer endpoints above handle; a raw cross-deployment `.workflow` file pasted into the API PUT is still rejected — transfer goes through export/import, not the content PUT.
- The **agent-block guard** (`AgentBlockGuard`) is the opposite: enforced at the shared seam every mouth crosses. `WorkflowSavePipeline.SaveCoreAsync` validates every Core graph it appends — the environment gate (`PlatformSettings:AgentRuntime:Enabled`), the allowed-model list, and the loop/parameterized-scope rules (which now refuse only Verification blocks and the references expansion cannot rewrite, see [Agent](../../guides/blocks/block-reference.md#agent)) — so shared-component fan-out, materialize, reconcile apply, duplicate, transfer import, and both plain save surfaces refuse identically rather than land agent content a deployment cannot save back. The three definition mouths that can introduce agent content without a template save (component create, definition replace, version restore — and transfer's component landings, even under a keep-mine template arm) run the same guard against the definition itself, refusing with `AgentRuntimeDisabled` / `AgentExpansionScope` / `AgentBlockInvalid`. Retire's definition mouth stays unguarded — retiring never validates the retiring component's own content — but the consumer rewrites it triggers still cross the pipeline seam: on a runtime-disabled deployment, a break-out whose consumer graphs carry agent blocks refuses like any other graph write and the retire rolls back whole. The cleanup route on such a deployment is to delete the agent blocks from those templates first — a graph without agent blocks always passes the gate.

## Hand-off notes for the next phases

- **Transfer shipped** — see "Transferring a workflow type between deployments" above. Lineage travels as ordered hash trails, never row ids. The bundle is a contracts DTO, so no top-level `SharedComponents[]` property was added to `Workflow` and the canonicalizer's transport suppressions are unchanged. Chain landing records one local version whose content is the bundle's — no foreign-row grafting, and `PayloadAbsentAt`'s shallow-import anticipation stays unexercised. `FormatVersion` was bumped to 3 when links, entries, and slot states became versioned transport; the current version is 4 (`Workflow.CURRENT_FORMAT_VERSION`), and a file declaring a newer one is refused with `This workflow file uses format version <n>, but this platform supports up to version 4. Update the platform before importing this file.` The bundle envelope's own version is 1 (`WorkflowTransferBundleFormat.CURRENT_VERSION`); a newer bundle is refused with `BundleFormatUnsupported`.
- **The Library-side definition editor GUI shipped** (C7): the `/library` detail view edits a component's head (Block or Section, refs composed in place) behind an impact-review dialog over `SaveSharedComponentContentCommand`, and a New-component flow authors from scratch through `CreateSharedComponentCommand` (`POST /shared-components`). Edit-in-consumer plus push remains a valid alternative loop, not the only one.
- **Bootstrap suggestions shipped** (the Library page's Suggestions panel, `ScanSharedComponentBootstrapQuery` — one query behind two mouths: the panel dispatches it in-process, and `GET /shared-components/suggestions` serves it over HTTP). The scan enumerates every workflow type, loads each template graph on demand (deliberately uncached, behind a Scan button with timing logged and disclosed), and groups not-actively-Linked sections and blocks by exact normalized content hash — **broken-out copies are candidates** (they are local content again; their provenance component is disclosed on the node row), while blocks inside an actively Linked section are never independent candidates. Content that could never usefully be shared is skipped outright: separator sections, sections with no blocks, and Loop Start / Loop End marker blocks. The skip is a `continue` inside an indexed loop rather than a filtered list, because the node's `TargetPath` is the API addressing key and `SharedComponentEditor.ResolveByPath` indexes the **full** ordered section list — dropping a separator from the list would shift every later `Sections[i]` and point promote at the wrong section. Because presentation is excluded from the hash, nodes that differ only in title, name, or group colour group together. Groups of two or more become suggestion cards — and so does a single stray whose hash equals an Active component's head (one orphaned copy is still worth attaching); a group matching an Active head offers "attach all" (the `?contentHash=` bootstrap lookup made guided), otherwise the card promotes the first checked node (name/category dialog) and attaches the rest via `PromoteSharedComponentCommand.AttachToComponentId`, per-node failures disclosed without stopping the sweep. Near-match similarity is deliberately out — exact hash only.
- **The stale-stamp window is self-healing**: reconcile-apply runs a restamp-only sweep over every workflow it saves anyway — any Linked node (no slot-state overrides) whose instance content hash equals its component's current head, rebuilt as [a stored hash](#content-normalization-and-the-comparison-contract) is, gets its `SharedComponentVersionHash` restamped with the head's stored hash, an administrative-field write riding the apply's own saves. Workflows the apply does not save stay stale on purpose and heal on their next fan-out.
- An unexpanded parameterized section IS promotable — the component carries the parameterization config; only expanded variants are rejected.

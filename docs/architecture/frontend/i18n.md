# Internationalization (i18n)

**On this page:** Configuration · Locale tree · Usage in components · Interpolation & pluralization · Shared terms · Escaping vue-i18n syntax · Adding or changing strings · Related pages

The IniaAi.Web frontend routes all user-facing copy through [vue-i18n](https://vue-i18n.intlify.dev/) running in Composition API mode. Every visible string lives in a JSON locale file under `src/assets/locales/en/`, addressed by a dot-separated key. English is the only implemented language today, but the message tree, barrels, and a compile guard are already structured so a second locale can be added by mirroring the `en/` tree.

## Configuration

The plugin is created in `src/plugins/i18n/i18n.ts`:

```ts
import { createI18n } from "vue-i18n";
import { LANGUAGES, DEFAULT_LOCALE } from "@/assets/locales";

export default createI18n({
  legacy: false,
  globalInjection: true,
  locale: DEFAULT_LOCALE,
  fallbackLocale: DEFAULT_LOCALE,
  messages: LANGUAGES,
  warnHtmlMessage: false,
});
```

| Option | Value | Effect |
|---|---|---|
| `legacy` | `false` | Composition API mode -- components use `useI18n()` instead of the Options API `$t` mixin |
| `globalInjection` | `true` | `$t` (and friends) are available directly in templates without importing |
| `locale` | `DEFAULT_LOCALE` (`"en"`) | Active locale |
| `fallbackLocale` | `DEFAULT_LOCALE` (`"en"`) | Falls back to English for any missing key |
| `messages` | `LANGUAGES` | The locale registry |
| `warnHtmlMessage` | `false` | Suppresses the warning when a message contains HTML |

`DEFAULT_LOCALE` and the `LANGUAGES` registry are defined in `src/assets/locales/index.ts`. English is currently the only entry:

```ts
export const DEFAULT_LOCALE = "en";

export const LANGUAGES = {
  en: EN,
};
```

## Locale tree

`EN` is assembled in `src/assets/locales/en/index.ts` from four top-level namespaces:

| Namespace | Source | Contents |
|---|---|---|
| `terms` | `en/terms.json` | The words several screens share and that may be renamed as a whole, each in the forms a sentence needs. See [Shared terms](#shared-terms) |
| `common` | inlined in `en/index.ts` | A handful of universal labels (`cancel`, `save`, `delete`, `close`, `confirm`, `done`, `loading`, `actions`, `details`) and the accessible-name helpers `actionFor`, `collapsePanel` and `expandPanel` |
| `page` | `en/page/` barrel | One JSON file per screen -- the copy specific to a single view |
| `shared` | `en/shared/` barrel | Cross-cutting copy reused across many screens (layout chrome, menus, enums, components, citations, tracer, dialogs) |

Both `page` and `shared` are directories of per-topic JSON files, re-exported through an `index.ts` barrel; `common` is a small object written inline rather than split into files.

### `page/` (per-screen)

`src/assets/locales/en/page/index.ts` re-exports one JSON module per screen: `login`, `twoFactor`, `twoFactorCode`, `forgotPassword`, `resetPassword`, `home`, `createWorkflow`, `workflowDetails`, `workflowExecutionLogs`, `tokenUsage`, `financialAnalysis`, `profile`, `counterpartyManagement`, `documentCategoryManagement`, `documents`, `signatures`, `modelPricingManagement` and `notFound`.

### Paid module copy

Each paid module keeps its copy in its own folder, under `src/modules/<module>/locales/en/`, and merges it into the same tree at run time. `openScreens.json` holds the text the app shows before any module screen opens, such as menu entries, and merges at startup. `page/` holds the rest, and merges when the module's first screen or piece opens. The open build lists no module in `PAID_MODULES` (`src/modules/index.ts`), so it merges none.


### `shared/` (cross-cutting)

`src/assets/locales/en/shared/index.ts` re-exports `layout`, `menu`, `enums`, `components`, `tracer`, `citations`, `aiPanel`, `workflowDownload`, `openDocuments`, `cancelExecution`, `deleteReport`, `reRunChoice`, `agentActivity`, `replayProvenance`, `dateRangeFilter`, `runFailure` and `modelRefusal`. The `components` file in particular is large -- it holds the reusable block/dialog copy that many views render.

## Usage in components

In Composition API components, pull `t` from `useI18n()` and reference keys by dot-notation. Some components alias it as `$t` to keep templates terse:

```ts
import { useI18n } from "vue-i18n";

const { t } = useI18n();
// or, to mirror the global template helper:
const { t: $t } = useI18n();
```

```vue
<template>
  <DialogTitle>{{ $t('shared.components.counterpartySelect.dialog.title') }}</DialogTitle>
  <Button variant="outline">{{ $t('common.cancel') }}</Button>
</template>
```

Keys are the full path through the message tree -- namespace, then file (module) name, then the nested object path inside that JSON. Real keys in the codebase look like `shared.components.counterpartySelect.dialog.title`, `page.login.title`, and `common.cancel`. Because `globalInjection` is on, templates can also use `$t(...)` without importing anything.

## Interpolation & pluralization

**Interpolation.** Wrap a placeholder name in `{ }` inside the message, then pass a values object as the second argument to `t()` / `$t()`. The placeholder name and the object key must match:

```jsonc
// page/counterpartyManagement.json
"dialog": {
  "deleteConfirm": "Delete {name}? Every @:{'terms.company'} beneath it is deleted too."
}
```

```vue
{{ $t('page.counterpartyManagement.dialog.deleteConfirm', { name: selectedCounterparty?.name ?? '' }) }}
```

The same mechanism handles numeric values. A number followed by a noun also needs the noun's singular and plural forms, as below: no English message writes `(s)`. `src/assets/locales/en/page/countPlurals.test.ts` fails on a message that does, and checks that each listed count line reads in the singular for one; each paid module carries the same test for its own copy (`src/modules/<module>/locales/en/countPlurals.test.ts`).

**Pluralization.** Separate the singular and plural forms with a `|` in the message, then pass the count both inside the values object (so `{count}` interpolates) and as a third argument (so vue-i18n picks the form):

```jsonc
// page/signatures.json
"editor": {
  "fieldCount": "{count} field | {count} fields"
}
```

```vue
{{ $t('page.signatures.editor.fieldCount', { count: block.fields.length }, block.fields.length) }}
```

The third argument is the plural selector; with it `0`/`2`/… render `"N fields"` and `1` renders `"1 field"`. Because `|` is plural syntax, a message that needs a literal pipe must escape it (see below).

## Shared terms

The `terms` namespace in `src/assets/locales/en/terms.json` holds a word that many messages use, once, so that renaming it is one edit. It holds the word for a counterparty, which every screen calls a company: `terms.company` (`company`), `terms.companies` (`companies`), `terms.Company` (`Company`) and `terms.Companies` (`Companies`). Each form has its own key because a linked message inserts the value as written, and a sentence needs the word in lower case mid-sentence and capitalised at the start or in a title.

A message that names the word links to the term instead of spelling it:

```jsonc
// page/counterpartyManagement.json
"title": "@:{'terms.Company'} Management",
"count": "{count} @:{'terms.company'} | {count} @:{'terms.companies'}"
```

`t('page.counterpartyManagement.title')` renders `Company Management`. Write the link in the brace form `@:{'terms.company'}`, never the plain form `@:terms.company`: vue-i18n 11 reads a plain link's key up to the next space, so a full stop, comma or closing bracket straight after it becomes part of the key and the link resolves to nothing.

Only the text a person reads takes the term. The keys, such as `page.counterpartyManagement`, the routes, such as `/counterparty-management`, the API fields and workflow placeholders such as `{Counterparty.Name}`, which a message writes escaped as `{'{Counterparty.Name}'}`, keep the name counterparty.

`src/screenTextSaysCompany.test.ts` guards the rule. It fails when an English message says counterparty, when a message spells company or companies itself instead of linking the term, when a component template shows counterparty as text or in a `title`, `aria-label`, `aria-description`, `placeholder`, `alt` or `label` attribute, or when a script holds a sentence literal that says counterparty. It also renders a title, a sentence and both plural forms of a count to check that the links resolve.

## Escaping vue-i18n syntax

> [!WARNING]
> The characters `{`, `}`, `|`, and `@` are **vue-i18n message syntax** -- they drive interpolation, pluralization, and linked messages. A literal one in a message string must be wrapped in the literal escape `{'...'}`, e.g. `"{'@'}"` for a literal `@` or `"{'{'}"` for a literal brace. An unescaped literal makes `t()` throw at render time, which unmounts whatever component referenced the key.

This is guarded by `src/assets/locales/localeMessages.test.ts`. The test walks every locale in `LANGUAGES`, with English replaced by the full tree of `src/test/helpers/messages.ts`, which merges every module's `openScreens.json` and `page/` copy the way the app merges them. It collects every leaf key and calls `t(key)` on each one -- a Vitest failure for any key whose template fails to compile. Run it as part of the normal unit-test suite (see [Testing](testing.md)).

## Adding or changing strings

1. Pick the right namespace and module: screen-specific copy goes in a `page/*.json`; copy reused across screens goes in a `shared/*.json`; truly universal verbs belong in `common`.
2. Add (or extend) the JSON file. If you create a **new** module file, export it from the matching barrel -- `en/page/index.ts` or `en/shared/index.ts` -- and add it to the corresponding object in `en/index.ts`.
3. Escape any literal `{ } | @` as `{'...'}`. Link a shared word to its term in the brace form, such as `@:{'terms.company'}`, rather than writing it out ([Shared terms](#shared-terms)).
4. Reference the new key by its full dot path via `t('...')` / `$t('...')`.
5. Run the locale-compile test to confirm every message still compiles.

> [!TIP]
> To add a second language, mirror the entire `en/` tree under a new locale directory, register it in `LANGUAGES` in `src/assets/locales/index.ts`, and the existing compile test will cover the new locale automatically (it iterates over every entry in `LANGUAGES`). Until then, `fallbackLocale` keeps any gap resolving to English.
